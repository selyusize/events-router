# Передать данные объектом

Массив в payload удобен ровно до тех пор, пока не нужно вспомнить, какие в нём ключи. Через месяц `$payload['amount']` превращается в угадайку: есть ли там `currency`, это рубли или копейки, а `order_id` строкой или числом?

Решение — DTO с именованным конструктором, который сам собирает имя события:

```php
--8<-- "typed-events/order-paid.php:dto"
```

Имя события пишется один раз, рядом с данными, а не в каждом вызове `dispatch()`:

```php
--8<-- "typed-events/order-paid.php:dispatch"
```

Слушатель получает тот же объект через `getPayload()`:

```php
--8<-- "typed-events/order-paid.php:listener"
```

```text
--8<-- "typed-events/order-paid.out"
```

Что это даёт:

- в месте рассылки видно, какое событие уйдёт;
- поля и их типы описаны в одном классе, IDE и Psalm их знают;
- `EventInterface` объявлен с шаблоном `@template TPayload`, поэтому у `Event<OrderPaid>` статический анализ знает тип payload.

Почему библиотека не собирает имя события из класса сама — в [Как это устроено](../explanation/design.md#no-magic).

Если DTO реализует PSR-14 `StoppableEventInterface`, слушатель может остановить рассылку — см. [Обработать ошибки](errors.md#stop).
