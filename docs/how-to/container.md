# Подключить контейнер

Слушателю почти всегда что-то нужно: почтовый сервис, репозиторий, HTTP-клиент. Создавать это руками в каждом слушателе — путь к дублированию и хаосу. Для этого есть контейнер.

## Без своего контейнера

Ничего делать не нужно. Роутер сам поднимает [PHP-DI](https://php-di.org) с автосвязыванием: классы с зависимостями в конструкторе создаются без регистрации.

```php
--8<-- "container/autowiring.php:classes"
```

```php
--8<-- "container/autowiring.php:example"
```

```text
--8<-- "container/autowiring.out"
```

Здесь работают два механизма:

- **Слушатель статичный**, поэтому зависимости он берёт сам: `Container::get(Mailer::class)`. `Container` — статический фасад библиотеки, `Selyusize\EventsRouter\Container\Container`.
- **Middleware — обычный объект.** Достаточно указать имя класса в `add()`, а контейнер создаст его со всеми зависимостями в момент, когда событие дойдёт до этого middleware.

## С контейнером проекта

Если в проекте уже есть контейнер, передайте его в фабрику:

```php
$events = EventRouterFactory::create($container);   // любой Psr\Container\ContainerInterface
```

С этого момента и middleware, и `Container::get()` в слушателях работают с вашим контейнером. Два контейнера не появятся.

В проекте на стартовой архитектуре с `Rasa\Container\Container` это выглядит так:

```php
use Rasa\Container\Container;

$events = EventRouterFactory::create(Container::getInstance());
```

Теперь `Rasa\Container\Container::get()` и `Selyusize\EventsRouter\Container\Container::get()` смотрят в один и тот же объект. В слушателях можно писать так, как принято в проекте.

## Другой контейнер

Роутеру подходит любой контейнер, реализующий PSR-11 `Psr\Container\ContainerInterface`. PHP-DI нужен библиотеке только как запасной вариант, когда своего контейнера нет. От контейнера роутер ждёт одного: `get(ИмяКласса::class)` возвращает объект этого класса.

| Контейнер | Что нужно сделать |
| --- | --- |
| PHP-DI (как в стартовой архитектуре) | ничего: создаёт любой класс сам |
| Laravel (`Illuminate\Container\Container`) | ничего: тоже создаёт классы сам |
| Symfony DependencyInjection | middleware и сервисы, которые слушатели берут через `Container::get()`, должны быть **публичными** сервисами с id, равным имени класса: по умолчанию сервисы Symfony приватные |
| простой контейнер «ключ → объект» | зарегистрировать каждый middleware, который указан в маршрутах именем класса |

Фасад `Container` — один на процесс. Если создать два роутера с разными контейнерами, `Container::get()` будет смотреть в последний переданный. В обычном приложении роутер один, и это не проблема.

## Если контейнер не создаёт классы сам

PHP-DI создаёт любой класс без регистрации. Другие контейнеры так умеют не всегда. Если ваш контейнер работает только с тем, что в нём зарегистрировано, зарегистрируйте в нём и middleware, которые указаны в маршрутах именем класса.

Иначе контейнер бросит исключение, когда событие дойдёт до такого middleware. Слушатель за ним получит статус `Failed`, остальные отработают как обычно.

## Если класса нет вовсе

Опечатку в имени класса роутер ловит сразу, ещё в `listen()` и `add()`, а не когда придёт событие. Исключение — [`InvalidRoute`](../errors/invalid-route.md), в стеке вызовов видна строка файла маршрутов с ошибкой.
